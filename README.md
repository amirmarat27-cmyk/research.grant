# Research Grant

Сайт для подачи и рассмотрения заявок на исследовательские гранты.

## Основные файлы

- `index.html` — внешний вид сайта, стили CSS и логика интерфейса на JavaScript.
- `app.py` — сервер на Python: регистрация, вход, заявки, роли и работа с базой данных.
- `requirements.txt` — библиотеки Python, необходимые серверу.
- `test_app.py` — автоматические проверки на временной тестовой базе.
- `render.yaml` — настройки запуска сервера на Render.
- `.gitignore` — список локальных файлов, которые не отправляются в Git.
- `.vscode/settings.json` — скрывает служебные файлы в проводнике VS Code.

## Локальный запуск в Windows

В терминале VS Code откройте папку проекта и выполните:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe app.py
```

Откройте в браузере `http://127.0.0.1:8000/`. Остановить сервер можно сочетанием `Ctrl+C` в терминале. Если порт 8000 занят, в новом терминале запустите:

```powershell
$env:PORT = '8001'
.\.venv\Scripts\python.exe app.py
```

Тогда адрес сайта будет `http://127.0.0.1:8001/`. Если папки `.venv` нет, создайте её командой `py -m venv .venv`, а затем установите библиотеки и запустите сервер командами выше.

## База данных

При локальном запуске без настроек облачной базы сервер использует SQLite-файл `research_grants.db`. Эта база отдельная от публичного сайта: локальные и облачные аккаунты и заявки не синхронизируются.

На Render для общей базы используется PostgreSQL в Supabase. Пароль базы задаётся в переменной окружения `SUPABASE_DB_PASSWORD` на Render, а не в коде. Не размещайте пароль в Git и не отправляйте его в чат.

Основные таблицы приложения: `users` — пользователи, `applicant_profiles` — тип аккаунта, `approval_roles` — права согласования, `access_tokens` — сессии, `collection_documents` — заявки, вложения и гранты, `proposal_events` — события заявок. Таблицы и другие служебные объекты самого Supabase могут отличаться.

## Как связаны роли

Студент или преподаватель заполняет и отправляет заявку. Эксперт оценивает её по четырём критериям. Затем заявка последовательно проходит заведующего кафедрой, комитет по этике и грантовый совет. Совет утверждает сумму финансирования; на любом этапе заявка может быть отклонена. Для начала согласования нужна хотя бы одна рецензия.

Администратор в разделе «Пользователи» выдаёт права эксперта и участников согласования. Один пользователь не может согласовать несколько этапов одной заявки, согласовать свою заявку или заявку, которую он оценивал как эксперт. Администратор не видит и не изменяет свою заявку в административном режиме, но может работать с ней в роли автора. Внешний эксперт при регистрации выбирает соответствующий тип аккаунта и ожидает назначения прав администратором.

После одобрения администратор планирует выплаты и сроки отчётов. Автор отправляет текстовые отчёты по этапам. Отметка о выплате ведёт учёт и не выполняет банковский перевод.

## Шифрование

Новые и изменённые заявки, новые записи журнала и новые вложения шифруются на сервере. Доступ к расшифрованным данным проверяется по роли. Для локальной SQLite ключ автоматически создаётся в `instance/document.key`; храните резервную копию ключа отдельно от базы. Без ключа данные восстановить невозможно.

Для PostgreSQL в Render перед публикацией необходимо создать и сохранить секретную переменную `DOCUMENT_ENCRYPTION_KEY` с постоянным ключом Fernet. Ключ можно сгенерировать локально командой:

```powershell
.\.venv\Scripts\python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Вставьте результат непосредственно в Render и сохраните резервную копию в безопасном месте. Не добавляйте его в код, Git или чат. Не меняйте ключ после записи данных без подготовленной процедуры миграции: иначе старые записи не расшифруются.

Ранее созданные незашифрованные заявки остаются читаемыми и шифруются при следующем изменении. Старые вложения и записи журнала автоматически не преобразуются; их миграция требует резервной копии и отдельной проверки. Приложение использует один серверный ключ и проверяет роли на сервере, а не отдельный криптографический ключ для каждой роли.

## Состояние требований проекта

- Реализованы регистрация и вход, аккаунты студента, преподавателя и внешнего эксперта, назначаемые права эксперта и трёх участников согласования, черновики и оценка по критериям.
- При новом сохранении заявки создаётся версия полей. Старые заявки получают историю только после следующего сохранения; история вложений и восстановление версии пока не реализованы.
- События создания и изменения заявки, назначения, рецензии, согласования, отчёты и бюджетные этапы записываются в журнал. События до добавления журнала не восстановлены; журнал не охватывает все действия системы и не защищён от изменения администратором базы.
- Реализована односторонняя слепая экспертиза: эксперт видит автора, автор не видит личности рецензентов и получает обезличенные баллы после решения. Двойная слепая экспертиза не реализована.
- Выплаты, их даты и сроки отчётов учитываются; текстовые отчёты можно отправлять через сайт. Автоматических платежей и напоминаний нет.
- Приложение остаётся учебным прототипом: старые документы и журналы могут быть незашифрованными, тип аккаунта при регистрации не подтверждается организацией, полного аудита безопасности нет. Не используйте систему для конфиденциальных или реальных исследовательских данных до проверки безопасности и миграции старых данных.

## Проверки

```powershell
.\.venv\Scripts\python.exe -m unittest test_app -v
```

Проверки создают отдельную временную базу и не изменяют локальные и облачные данные сайта.
